## 角色

| 角色 | 說明 |
|------|------|
| 醫事司 | 主管機關。外加容額全程由其操作；容額填報的公告者；容額成果報告的確認/歸檔者 |
| 醫策會 | 醫策會。容額填報的初審與分組會議、RRC 安排；外加容額成果報告的協同審查方之一 |
| RRC | 專科醫師訓練計畫認定會。容額填報的大會審查 |
| 醫學會 | 各專科醫學會（25 個）。容額填報與容額成果報告的填報方 |
| 訓練醫院 | 外加容額的申請方（系統外發函）；外加容額成果報告的提交方（系統外發函） |

> ⚠️ 目前為 mock 原型，**不做角色權限區分**，所有畫面皆可完整操作。上表是「真實情境下誰做什麼」，用於理解流程，非目前的權限實作。

## 容額填報 ✅

醫事司發起、醫學會填報、多階段審查、最後公告的主流程。

### 狀態機

```
醫事司於管理專區設定「容額填報開放」
      ↓（開放後醫學會才可填報）
醫學會填報 → 送件
      ↓
醫策會初審
      ↓（通過）
分組會議審查（醫策會內部安排）
      ↓
RRC 大會審查
      ↓
醫事司審查（非容額決策的最後把關：錯字、法規引用等，可退件）
      ↓
審查通過 ── 案件離開審查作業區，交棒公告管理（見「公告管理」節）
```

> 2026-07-31 更新：終點由「醫策會更新大會審查結果 → 推進至待公告 → 醫事司公告 → 已公告」
> 改為上述鏈。**「待公告／已公告」不再是審查鏈的階段**——那是公告管理內部的概念（案件在那裡
> 走「待製作 → 已製作 → 已公告」）。審查專區新增「已審結」唯讀分頁，供追溯已審查通過的案件。
>
> 容額成果報告是與本審查鏈**時間上不耦合的獨立流程**（可早於送件即完成），不在此鏈上，見下方專節。

### 退件規則 ✅（重要）

- 任一階段皆可退件，案件**直接退回醫學會**修正。
- 醫學會重新送件後，**由退件的單位接續審查**，不重走整條鏈。
  - 例：案件已過 RRC、進到醫事司，醫事司退件 → 醫學會修正重送 → **直接回到醫事司**，不再走「醫策會 → 分組會議 → RRC」。
- 實作含義：案件需記錄「退件返回的階段（resumeStage）」，重送後跳回該階段，而非從頭。

### 與容額成果報告的關係 ✅

- 容額成果報告是**與本審查鏈時間上不耦合的獨立流程**：醫學會可自「待送件」起上傳，
  無須等到任何審查階段（見「容額成果報告」節）。
- 成果報告**不影響審查與公告作業**，是醫事司留存的案件歸檔附件，兩條流程平行。

## 容額成果報告 ✅

> ⚠️ **命名陷阱**：客戶要求維持「容額成果報告」此 wording，但其核心意義**不是**容額執行成效，
> **也與 RRC 無關**。實質內容是「**醫學會對各申請醫院的內部評估結果**」——醫學會先評估各家訓練
> 醫院，產出此報告，再據以填寫「核發多少容額給各醫院」的容額申請表。故此報告理論上**先於**容額
> 申請完成，是申請的依據，也是醫事司歸檔案件時所需的附件。設計時勿被標題誤導。

### 流程 ✅

```
醫學會內部評估各申請醫院 → 產出成果報告
      ↓（全程可上傳，最早自「待送件」起，與審查階段無關）
醫學會上傳 → 送出
      ↓（直接給醫事司，不經醫策會）
醫事司：確認 → 歸檔（作為容額申請案件的附件）　／　有需要 → 退回補件
```

- **與審查流程時間不耦合**：可在「待送件」階段就上傳，deadline 甚至早於送件給醫策會初審。
  與容額填報視為**兩條獨立流程**。
- **無醫策會參與**。醫學會 ↔ 醫事司 直接往來，走不同於容額申請的文件路徑。
- 內容是醫學會對各申請醫院的評估結果，是容額申請的**依據**；醫事司留作**案件歸檔的附件**。
- 仍依附在容額填報案件（同一醫學會／案件），但生命週期獨立於審查階段，非「待公告後的子任務」。

### 上傳與審查的surface分離 ✅（權限邊界＝路由）

- **上傳（填報專區，醫學會）**：`/filing/quota-filing/outcome-report`，容額填報的**子頁面**
  （2026-08-06 由頁內區塊改；原區塊高 558px，佔掉容額填報頁整個第一屏，把該頁自己的內容擠到
  下面）。容額填報頁只留一列帶狀態的入口——狀態必須在該頁可見（尤其「退回補件」），故入口列
  帶 badge 與退件意見摘要，不是一個沒有訊息的按鈕。**全程可上傳、不以審查階段 gate**。
- **不獨立成模組（不進 nav）**：沒有權限外溢問題——只有醫學會 ↔ 醫事司，與容額填報同一批人
  （外加容額成果報告拆成獨立模組是因為醫策會要參與）。且 nav 若並列「容額成果報告」與
  「外加容額成果報告」，兩個名稱極像、流程完全不同，是已知的混淆點。
  **升級為獨立模組的判準**：出現第三方參與者造成權限外溢／收的內容由純上傳變成要逐醫院填評估／
  使用者開始「專程來交報告」而非填報時順手交。
- **確認/退回（審查專區，醫事司）**：獨立surface「容額成果報告審查」，醫事司看送來的
  補件並確認歸檔或退回補件。醫學會不能確認自己上傳的報告，故上傳與審查分屬兩路由。
- 由現有 `/review/outcome-report`（「成果報告審查」）改造而成，**並移除其中的「醫策會初審」
  中間步驟**（容額成果報告不經醫策會，原實作建錯）。
- 審查專區子導覽：文件填報審查｜容額填報審查｜**容額成果報告審查**。

### 實作 ✅（2026-07-17 對齊上傳/審查分離；2026-07-29 時間解耦已完成）

- 填報端：容額成果報告區塊在 `/filing/quota-filing`。`showOutcomeReport` 已改為全程顯示
  （`components/filing/quota-filing-view.tsx`，不再以審查階段 gate）。
- 審查端：`/review/outcome-report`（容額成果報告審查）醫事司確認歸檔／退回補件。✅
- 舊的「醫策會上傳＋初審」模型已移除。✅

## 外加容額管理 ✅

登錄 → 審查 → 公告，全程醫事司單一角色。已於 `feat/additional-quota-upload-part2` 實作。

### 狀態機

```
醫事司登錄申請（醫院來文）→ 待審查
      ↓（內部會議後登錄審查結果）
審查通過 ── 案件到此為終點；公告（含文號）完全由公告管理辦理，案件身上不帶公告欄位
```

> 2026-07-31 更新：全線一致（見「公告管理」節），案件終點統一為「審查通過」，不再有
> 「待公告／已公告」案件階段。是否已公告改由公告管理**反查**（`isCaseAnnounced`），
> 外加容額成果報告據此判斷「公告滿一年」，不再讀案件自身的公告欄位。

- 唯一鍵為申請項目 uid（同院可在不同分科各自申請）。
- 容額上限為硬限制：核定容額 + 申請容額 > 上限即不得送出。
- 分類原則為可維護的選項，升級為 `{ 名稱, 需成果報告: on/off }`；「需成果報告」開關
  決定該案公告滿一年後是否需提交外加容額成果報告（見下方「外加容額成果報告」）。
- 公告為跨案件的滾動彙整（全年隨時可再申請、再公告加入同一份公告），**非單案欄位**，
  由 `announcement-management` 辦理。完整滾動公告設計待全系統完成後再評估。💡

## 容額微調 ✅（2026-08-05 定案並實作）

> 醫學會在**既有訓練醫院之間搬動容額**。總容額不變——有醫院調增，就有醫院調減。

### 流程 ✅

```
醫學會於系統外形成共識 → 醫學會填報（選醫院、填調整後容額、上傳附件）
      ↓
醫事司審查（可退件）→ 審查通過 → 公告發文
```

- **審查鏈只有醫事司一段**：不經醫策會初審、分組會議、RRC 大會。
- 終點「審查通過」＝交棒公告管理，與其他三線一致。
- **退件為一等狀態**（`returnedFrom`）：退回醫學會補正，重送後回醫事司續審。
- 案件粒度＝**醫學會 × 年度 × 第 N 次**（婦產科來文為「第 1 次微調」，同年度可多次）。

### 核心不變量：總容額守恆 ✅

微調只是搬動，增減必相抵為 0。**醫學會送出前硬擋**不平衡的案件，不留給醫事司事後才發現。
畫面即時顯示調增／調減／淨變動／異動家數。

醫事司審查時最重視的是「**哪間醫院減、哪間醫院增**」，故列表層級就把調增／調減攤開，
詳情頁的版面順序為 結餘 → 只列異動醫院的對照表 → 調整後完整名單 → 附件 → 歷程。

### 輸入方式：填「調整後容額」，增減由系統算 ✅

兩份參考公文（`ref/婦產科及兒科微調容額的公文及附件/`）格式不同：

| | 婦產科（115/06/01） | 兒科（115/06/04） |
|---|---|---|
| 表格欄位 | 原公告 → 擬微調為（前後絕對值） | 核定容額 ＋ 申請微調容額 ＋ 微調原因 |
| 異動家數 | 14 家 | 2 家 |
| 總量 | 25 → 25 | 維持 130 |

**兒科格式的數字沒有方向**——兩筆的「申請微調容額」都是 1，是增是減只能從原因欄
（「釋出容額」vs「招收住院醫師」）判讀。兒科另在完整名冊裡用 `12→11` 就地標示異動。

故系統統一收**調整後容額**，增減量與方向一律由系統推算：前後值可推導出增減量，
反之不行。格式落差因此在系統內消失，推算結果也直接就是醫事司要的「誰增誰減」。

### 其他決策 ✅

- **基準容額（原公告）自容額填報帶入**，不可編輯；排除聯合申請的 sub-row（容額由主訓機構統籌）。
- **只能在已認定合格的醫院之間搬動**，不能憑空新增醫院（兩份公文的對照表都落在既有名單內）；
  加選醫院的挑選器範圍即為該醫學會容額填報送過的訓練機構。
- **調成 0 是合法值**（婦產科有多家調成 0）。
- **微調原因選填**，且僅在該列有異動時可填。
- 公告端與外加容額**共用「外加/微調容額」來源 tab**（07-31 決策 #2）；該 tab 的次要欄名
  為中性的「申請單位」——外加的主體是訓練醫院、微調是醫學會。該 tab 另有**類型欄與類型篩選**
  （`PendingCase.caseKind`），且**公告文件依類型分別套版**：外加＝某院某分科外加容額表、
  微調＝原公告／調整後／增減對照表；同批混選兩種類型時提醒。
- **案件是一等物件**：一個醫學會同年度可有多次微調，故有列表（`/filing/quota-adjustment`）
  與明確起點（`/new`，只選年度，第 N 次自動算）。
- **兩端視角不同，欄位隨之不同**：
  - 填報端＝**單一醫學會**（`CURRENT_SOCIETY_ID`，實際系統由登入身分決定）。使用者只有自己
    一個科，故新增時**不選醫學會**，列表也不列醫學會與科別欄；首欄為「第 N 次」，
    依年度與次數**降冪**，最新一次在最上方。
  - 審查端＝**跨醫學會**（醫事司）。以科別辨識案件（與醫學會一對一且較短），「次數」為必要欄位。
  - 增減的細節放在詳情頁的異動對照表，兩端列表都不攤開。
- **同年度未審結前不得新增下一件**：基準容額＝原公告疊加已通過的微調（`getEffectiveBaseline`），
  若兩件並行，各自平衡但合併後可能讓某醫院容額變負數。
- **聯合申請的合作機構隨主訓機構帶入呈現**：唯讀、無容額（掛主訓機構）、不計入守恆；
  移除主訓機構時整組移除。微調不能改變聯合申請的組成——那是容額填報的事。

> 未納入：婦產科來文的 `*` 註記（該容額含偏鄉／緊急醫療支援政策的 +1 名）目前不建模。

## 外加容額成果報告 ✅

> 外加容額案件**公告執行滿一年後**，需訓練醫院提交成果報告。

### 適用範圍 ✅

- **只有特定「分類原則」的外加容額案件**需要提交（非全部）。目前為「支援偏鄉」。
- **由分類原則的「需成果報告」開關決定，不以名稱硬比對** —— 分類原則選項升級為
  `{ 名稱, 需成果報告: on/off }`，維護彈窗每項附一個開關。避免改名導致追蹤列表失聯。
- 觸發時點：案件公告後滿一年。

### 權限邊界與模組歸屬 ✅

- 外加容額的**申請＋審查**全程醫事司單一角色（合併於外加容額管理頁）。
- 但成果報告涉及**醫策會**。若把醫策會評論欄塞進外加容額管理頁，後端授權會外溢
  （醫策會將能做容額填報＋審查），非所欲。
- **決策：外加容額成果報告為獨立模組（自己的路由與 nav 入口）**，醫事司與醫策會皆授權
  進此模組，授權不外溢到外加容額管理。權限邊界＝路由，非頁面內欄位級。
- 外加容額管理的案件頁僅放唯讀「本案需成果報告 → 前往」連結；可編輯評論在成果報告模組。
- 現有 nav 的「成果報告上傳」入口**保留但收斂為「外加容額成果報告」**
  （容額成果報告改依附容額填報案件，離開此入口）。

### 流程 ✅

```
訓練醫院系統外發函 → 醫事司 ＋ 醫策會（兩單位皆收到）

醫事司、醫策會分工協調 → 由其中一方擇一負責審查、留下評論 → 儲存歸檔
```

- 用途：該醫院**後續年度再申請外加容額時，作為審查評斷的依據**。
- 涉及醫策會（外加容額的申請/審查本身不涉及醫策會，僅此成果報告涉及）。

## 公告管理 ✅（業務邏輯已與客戶確認 2026-07-31；UI 分階段實作中）

三條主線的終點都回到醫事司辦理公告：**文件填報審查、容額填報審查、外加容額**。
（容額成果報告與外加容額成果報告終點是歸檔，**不產生公告**。）

> 頁面結構、實作現況與待建置清單見 **`docs/announcement-module-plan.md`**。本節記流程與狀態機。

### 審查 → 公告的交棒點：「審查通過」 ✅

審查鏈的終點是醫事司點擊「審查通過」，這是審查與公告兩條流程的交棒點：

```
醫策會初審 → 分組會議 → RRC大會 → 醫事司審查 →〔審查通過〕
                                    │ 醫事司最後把關          │ 交棒公告管理
                                    ▼                         ▼
                          （錯字、法規引用等          案件離開審查作業區，
                           非容額決策，可退件回醫學會） 進入公告管理的待公告池
```

- **新增「醫事司審查」階段**（RRC 後、審查通過前）：RRC 通過後，醫事司仍會再檢查一次
  非容額數字分配的可修正處（錯字、引用法規等），可退件回醫學會修正，也可審查通過。
- **「審查通過」＝交棒**。此後案件離開審查作業區。**審查專區不再有「待公告／已公告」階段**
  —— 那是公告端概念。「待公告」全系統只出現在公告管理一處，避免同名混淆。
- 三線皆適用。外加容額全程醫事司單一角色，其「審查通過」＝醫事司登錄審查結果那一刻。
- 「審查通過」歸醫事司（不是醫策會），因醫事司要做上述最後把關。

### 待公告 → 公告的兩條獨立路徑（解耦）✅

案件審查通過進「待公告」後，醫事司有**兩件互相獨立、不強制先後**的下一步：

| 路徑 | 產物 | 粒度 | 策略 |
|------|------|------|------|
| 系統內公告 | 系統內發布，給醫策會／醫學會檢視 | 一篇可涵蓋多案 | **最簡**：標題＋內文＋附件 |
| 官網公告文件 | 正式公文文件（Word→PDF），拿去衛福部官網發文 | **每醫學會一份** | 套版產出，人工補文號 |

- 兩步驟各自「已完成／未完成」，不綁死流程順序：使用者常只做一件、或分不同時間做，硬綁成一步
  反而製造假的先後、增加認知負擔。
- 案件的公告端狀態（衍生自官網公告文件是否已產出／是否已被系統內公告引用發布）：
  `待製作 → 已製作（待發布） → 已公告`。**沒有「延後」狀態**——未處理的案件就一直留在待製作，
  不需要額外的隱藏/還原機制。
- **兩個任務分屬兩個獨立模組（2026-08-05 定案，07-31 的頁內 tab 版已作廢）**：
  - **公告文件製作** `/announcement-documents`：對象是**案件**。階段分頁為 待製作／已製作
    （2026-08-05 由三段收斂；「是否已發站內公告」改以表格「系統內公告」欄表達——有日期＝已公告、
    無＝待發布）。**已公告案件不移出視野**——使用者做完站內公告後仍需下載檔案去官網，且拆成
    兩個模組後沒有 tab 可跳去對照，本工作台必須自答「還缺哪一步」。已公告者不可再被帶入站內公告。
  - **站內公告管理** `/announcement-management`：對象是**一篇站內公告**（前台公告欄）。起點只有
    新增公告、或點一則公告檢視／編輯。
  - 兩者對象不同（案件 vs 公告），故不再用頁內 tab 併為一個模組；入口平列於 nav 管理專區。
  - **銜接是雙向的**：工作台可選取多筆「已製作」案件帶入組稿（捷徑）；組稿頁也可自行
    「加選公告文件」瀏覽已製作、未被引用的文件。故站內公告可獨立完成，不必先經工作台。

### 官網公告文件：以醫學會為單位，文號掛在案件層級 ✅

依 `ref/115年度…認定合格名單` 的實際公文推得（**重要，推翻了初版「一公告一文號」的假設**）：

- **產出以醫學會為單位**（容額、文件審查皆是），格式比照認定合格名單公告：表頭＋醫院容量表。
- **文號與修正歷程掛在「案件（醫學會）」層級，不是掛在公告批次**：
  - 一次發文文號多科共用（各科以字尾字母區分，如 …796A／…796D／…796J），但**每科一份文件、
    各自帶自己的文號**。
  - **修正逐科、非同步**：每次修正在該科文件表頭疊一行文號、標題前 +「第 N 次修正」。
    （範例：婦產科第 2 次修正 = 原始 3/19 + 6/1 修正 + 6/16 修正，三行文號堆疊。）
- **文號為人工輸入字串**，系統不管理、不驗證格式，但**沒有文號不得發布**。
- 「沒有文號不得發布」在本模型下的落點（2026-08-05 釐清）：**引用型站內公告**（引用了公告文件）
  本身不另設文號——文號在各份文件上，且製作文件時已強制輸入；**自建型站內公告**（未引用文件，
  如作業時程、說明會通知）公告本身即公文，其文號為必填且實際擋發布。
- **更正公告採版本鏈**（已發布不改內容，另建更正稿保留鏈）—— 沿鏈即可組出上述堆疊表頭；
  這也是日後**容額微調**產生後續公告要用的同一機制。
- **產出／下載一律後端處理，前端只放按鈕**；mock 不做真下載、不真的產檔（見用詞規範）。

### 公告狀態的權責歸屬：公告管理獨佔，其他模組反查 ✅（2026-07-31 補充）

「某案件是否已公告、其文號與日期」**由公告管理擁有**，**不回寫到來源案件身上**：

- **外加容額管理**：案件到「審查通過」即為終點，**不顯示、不連動公告文號**；外加容額案件身上
  不帶 `announcementDate`／`announcementNumber`。審查通過頁僅留一句中性指路「後續公告由公告管理辦理」。
- **外加容額成果報告**：判斷「公告滿一年需交報告」的依據，改為**反查公告管理**（哪一份已發布公告
  涵蓋了此案件），而非讀案件身上的公告欄位。
- 同理，審查專區「已審結」顯示的公告狀態也是反查公告管理，不在審查案件上存公告資料。

### 已審結：審查專區內的唯讀歸檔 ✅

案件層級的歸檔區（在審查專區內，唯讀）：可搜尋、可追溯，看得到當初審查歷程與文件、
也看得到公告文號／修正歷程。用途是審結後仍能翻找某案當初的審查過程紀錄。

### /document-archive 已移除（2026-07-31）✅

資訊架構已按模組拆開（外加容額／容額／文件填報／審查各線），文件天然歸屬各自模組＋案件下；
「翻當初審查紀錄」由上述「已審結」涵蓋。跨模組把全部文件混一起再搭一套搜尋／分類邏輯，
與模組化 IA 打架、維護重複邏輯，只服務少數「忘記在哪」情境，故移除。
未來若出現明確的全域檢索或稽核調閱需求再議（屆時可由各模組資料重建）。

### mock 保真原則（實作規範）

本系統為 mock 原型。**凡「之後由後端處理」的能力（下載、產檔、寄送等）一律只做按鈕**，
